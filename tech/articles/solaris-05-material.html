マテリアル — MaterialX と Material Library

houdini-solaris / 2026-08-19

出典: SideFX 公式ドキュメント Material Library / Assign Material / MaterialX / Karma。 このページは上記を日本語で要約・再構成した学習メモです。 マテリアルの構造と割り当ての結果は Houdini 22.0.368 の実機で確認しています。

この記事で扱うこと

  • USD のマテリアルがどういう形をしているのか
  • MaterialX / Principled Shader / USD Preview Surface の使い分け
  • materiallibrary と assignmaterial のノード解説
  • 実機でマテリアルを1つ作って、プリムパターンで3つに割り当てます

マテリアルは「箱」で、シェーダは「中身」

ここだけ最初に押さえておくと、あとが楽です。

USD のマテリアルは2階建てになっています。 Material という箱があって、その中に Shader が入っています。

/materials/brick          Material   ← 箱。ジオメトリはこれを指します
└─ brick                  Shader     ← 中身。実際の計算をするもの

ジオメトリが結びつくのは箱のほうです。中身が何であっても、外から見れば同じ「brick というマテリアル」。 だからレンダラごとに中身を差し替えても、割り当てはそのまま使えます。

この作りが分かっていると、シーングラフでマテリアルを開いたときに 「なんで2段になっているんだろう」と迷わなくなります。

シェーダは3系統ある

Houdini で作れるシェーダは大きく3つで、それぞれ守備範囲が違います。

MaterialXPrincipled ShaderUSD Preview Surface
正体業界標準の規格Houdini 独自USD 標準の最小セット
Karma CPU○○○
Karma XPU○×○
他のレンダラ対応が広い×ほぼどこでも
表現力高い高い低い（簡易表示向け）

迷ったら MaterialX です。XPU でも他のレンダラでも通りますし、 第0回で書いたとおり Karma XPU は Principled Shader を扱えません。 最初から MaterialX で組んでおくと、あとで engine を切り替えたくなったときに困りません。

Houdini 20 から、Material Library の中にシェーダを置く方法が変わりました。 いきなりシェーダを置くのではなく、ビルダー（Karma Material Builder / USD MaterialX Builder など）の subnet を作って、その中に置くのが正しい形になっています。 こうすることで、混ぜてはいけないノードがタブメニューに出てこなくなります。

実機で組んでみました

MaterialX の Standard Surface を1つ作って、前回のシーンに割り当ててみます。

1. シェーダを1つ置いたら、プリムが4つできた

materiallibrary の中に mtlxstandard_surface を1つ置いただけで、 ステージにはこれだけできていました。

/materials                 Scope
└─ brick                   Material
   ├─ brick                Shader   ← 置いた MaterialX
   └─ brick_preview        Shader   ← 勝手に増えた

brick_preview は自動で作られた USD Preview Surface です。 Material Library の Auto-generate Preview Surface Shaders が既定でオンなので、 MaterialX を1つ書くたびに、その簡易版が一緒に作られます。

これは親切な仕様です。USD Preview Surface は USD の標準なので、 Karma を知らないソフトに渡しても、とりあえず色は出ます。 本命のシェーダと、どこでも通る保険。その2枚組が1つの箱に入っている、という形ですね。

2. パターンで割り当てたら、3つに刺さった

assignmaterial の Primitives に %type:Cube と書いて、 Material Path に /materials/brick を入れました。結果です。

マテリアル結びついたプリム
/materials/brick/asset/geo
/shelf/copy1/geo
/shelf/copy2/geo

パスを3つ書いたわけではありません。「立方体ぜんぶ」と書いただけです。 第3回のプリムパターンが、そのまま効いています。

面白いのは、/shelf/copy1/geo と /shelf/copy2/geo は 前回リファレンスで持ってきたプリムだということです。 参照先のファイルには一切触らずに、こちら側のレイヤーに 「このプリムはこのマテリアル」という一行を足しただけで結びつきました。 第2回のルール3（ディスクのファイルは書き換えない）が、ちゃんとここでも効いています。

ノードごとの解説

Material Library materiallibrary

やることシェーダの VOP ネットワークを、USD の Material プリムに変換する
入力0〜1
要のパラメータmatpathprefix（既定 /materials/）、Material VOP（既定 *）
中身の作り方ノードに潜って、ビルダー subnet を作り、その中にシェーダを組みます
Auto-generate Preview Surface既定オン。USD Preview Surface が自動で付きます

公式ドキュメントに1つ推奨が書かれています。 このノードでも割り当てはできるけれど、割り当ては別ノードに分けたほうがよい、と。 作るのと配るのを分けておくと、あとから見た人が読みやすいからですね。

Assign Material assignmaterial

やることマテリアルをプリムに結びつける
入力0〜1
要のパラメータPrimitives（プリムパターン）、Material Path
指定方法Explicit Path ／ CVEX Script ／ VEXpression
複数まとめて行を増やせば、1ノードで何組でも割り当てられます

VEXpression が使えるのが Houdini らしいところです。 プリムごとに違うマテリアルを計算して返せます。

return (@elemnum % 2) ? "/materials/rough_red" : "/materials/rough_blue";

これで奇数番目と偶数番目に別のマテリアルが入ります。 @primpath（プリムのパス）や、そのプリムの属性も変数として使えます。

Material Binding の Method も覚えておくと効きます。

Method意味
Direct（既定）該当するプリム1つずつに書き込む
Collection Basedコレクションそのものに書き込む

コレクションに割り当てるなら Collection Based にします。 そうすると、あとからコレクションにプリムを足したときに、割り当てが自動で追随します。 第3回のコレクションが効いてくる場面です。

Component Material componentmaterial

やることアセット単位でマテリアルをまとめて管理する
向いている場面Component Builder で作ったアセットに、マテリアルのバリエーションを持たせたいとき

Material Linker materiallinker

やることマテリアルとプリムの結びつきを、専用の UI でまとめて編集する
向いている場面割り当てが増えてきて、ノードを並べるのがつらくなったとき

実機で気づいたこと

Preview Surface が「勝手に増える」のは正常

シェーダを1つ置いたのに Shader プリムが2つできて、最初は何かを間違えたのかと思いました。 これは Auto-generate Preview Surface Shaders の仕業で、正常な動作です。

切りたい場合はチェックを外せます。ドキュメントには、 テクスチャの不透明度の扱いで Storm が意図しない表示になることがあり、 そのときは自動生成を切って手で組む、という回避策が載っていました。

マテリアルの「箱」の名前は、シェーダのノード名から来る

ノード名を brick にしたので、できたのは /materials/brick でした。 matpathprefix（既定 /materials/）＋ノード名、という組み立てです。

第4回のバリアント名と同じで、ノード名がそのまま USD に残ります。 Solaris はこのパターンが多いので、ノード名は最初からきちんと付けておくのがよさそうです。

詰まりやすいポイント

  • Material Library の中にシェーダが置けない → Houdini 20 以降はビルダー subnet の中に置きます。 いきなり置く形は非推奨になりました。
  • XPU に切り替えたら真っ黒 → Principled Shader は XPU では動きません。MaterialX に置き換えます。
  • 割り当てたのに色が出ない → Material Path の綴りを確認します。 /materials/ の prefix を忘れがちです。
  • コレクションに足したプリムに色が付かない → Method が Direct のままです。 Collection Based にすると追随します。
  • Shader プリムが2つある → 正常です。片方は自動生成された Preview Surface。

次回

マテリアルが付いたので、次はライトとカメラです。 第0回で「ライトが無いと真っ黒、カメラが無いと何も映らない」と書いたところを、 1つずつノード単位で見ていきます。 ライトの種類、明るさの単位、Light Mixer、そしてカメラの各パラメータが USD 側でどう保存されるかを扱います。
