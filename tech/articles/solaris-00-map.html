Solaris と Karma の地図 — 何が複雑なのかを先に整理する

houdini-solaris / 2026-08-19

出典: SideFX 公式ドキュメント Solaris and USD / How LOPs work / Karma / Karma User Guide、 および USD Basics with Solaris（英語）。 このページは上記を日本語で要約・再構成した学習メモです。ノード名とパラメータの既定値は Houdini 22.0.368 の実機で照会して確認しています。

このシリーズについて

Solaris と Karma は、触りはじめたときの「覚えることの多さ」がなかなか手強いところだと思います。 私自身、ワークフローに組み込みたいと思いながら何度か引き返しました。そこで、公式ドキュメントを 読み直しながら、実際に使う順番で並べ直したマニュアルを作ることにしました。

方針は3つです。

  • USD の理論は最小限にします。 USD の仕様そのものより、Solaris で作業するときに 知らないと詰まることを優先します。
  • ノード名とパラメータ名は正確に書きます。 記憶で書かず、Houdini 22.0.368 に 問い合わせて確認したものだけを載せています。
  • 絵を出すところまでを1周させます。 概念の説明で終わらず、Karma で レンダリングして書き出すところまで通します。

なぜ複雑に感じるのか

Solaris が難しく感じる理由は、たぶん「難しいものが1つある」のではなく、 性質の違う3つを同時に覚えさせられることにあります。

層正体つまずきやすいところ
USD シーンを記述するファイル形式とデータモデル。Houdini とは別に存在する規格 レイヤー、リファレンス、オピニオンといった聞き慣れない語がまとめて出てくる
Solaris / LOPs その USD をノードグラフで手続き的に組み立てる Houdini 側の仕組み SOP と見た目が同じなのに、線を流れているものの正体が違う
Karma その USD を絵にするレンダラ サンプリング系のパラメータが多く、どれがどのノイズに効くのか分かりにくい

逆に言うと、この3つを切り分けてしまえば、それぞれはそこまで大きくありません。 このシリーズもその順で進みます。

いちばん大事な一行

細かい話に入る前に、これだけ先に書いておきます。

SOP の線を流れているのはモノ。LOP の線を流れているのはシーン。

SOP のノードは、渡されたジオメトリを加工して次に渡します。箱を Subdivide に通せば、 分割された箱が出てきます。流れているのは「モノ」です。

LOP のノードは違います。入ってくるのはシーン全体で、出ていくのもシーン全体です。 ノードがやるのは、そこに変更をひとつ書き足すことだけ。 「ライトを1つ足す」「このプリムを隠す」といったメモを1枚重ねて、シーンごと次に渡します。

Photoshop のレイヤーが近いと思います。レイヤーを1枚足しても、画面に出るのはそのレイヤー単体ではなく、 全部を重ねた1枚の絵ですよね。LOP も同じで、どのノードを見ても その時点でのシーンの完成形が表示されます。

この「書き足したメモがどこに置かれるか」がレイヤーの話です。第2回で扱います。

まず1枚出すまで — これが基本形です

Blender の Cycles なら、オブジェクトを置いて F12 を押せば絵が出ます。 Solaris は同じ感覚でいくと出ません。ここが最初の壁だと思います。

理由ははっきりしていて、Solaris のステージは最初、本当に空っぽだからです。 既定のライトも、既定のカメラもありません。全部ノードで載せます。 裏を返すと、載せるものさえ決まっていれば毎回同じ形で組めます。

最小構成はこの4つです。上から順に1本の線でつなぐだけで、分岐もありません。

この図でいちばん言いたいのは、いちばん下の一致です。実機で確認しました。

camera LOP の Primitive Path 既定値/cameras/$OS
$OS はノード名なので、camera1 が作るプリムは/cameras/camera1
karma LOP の Camera 既定値/cameras/camera1

つまりカメラノードを1つ置くだけなら、Karma 側は何も触らなくていいということです。 既定値どうしが噛み合うように作られています。2つ目のカメラを足したときや、 ノード名を変えたときだけ、karma の Camera を合わせにいきます。

この4つを実際に Houdini 22.0.368 で組んで確認しました。karma のパラメータは 何ひとつ触っていませんが、ステージには /lights/domelight1 と /cameras/camera1 が並び、 レンダー設定の /Render/rendersettings まで自動で作られていました。 ビューポートの表示方法を Karma CPU に切り替えると、そのまま絵が出ます。

絵が出ないときに疑う順番も、この4つで決まります。

症状たいていの原因
真っ黒ライトが無い
何も映らない／変なところを映しているカメラが無い。または karma の Camera が別のパスを指している
ジオメトリだけ出ないそもそもステージに載っていない（第1回の話です）

あとは全部、この4つのすき間に挟まるものです。マテリアルは 1 と 2 のあいだ、 レイヤーの整理も同じあたり、レンダー設定は 4 の手前。 シリーズの残りは「この骨格のどこに何を足すか」という話になります。

全体の流れ

ざっくりした流れはこうなります。左から右に一方通行です。

SOP（ジオメトリを作る）
   │  SOP Import / SOP Create / SOP Modify
   ▼
LOP = /stage（シーンを組む）
   ├─ ステージに載せる ……… ジオメトリ・カメラ・ライト
   ├─ レイヤーを整理する …… SubLayer / Layer Break / Configure Layer
   ├─ マテリアルを割り当てる  Material Library / Assign Material
   └─ レンダー設定を作る …… Karma Render Settings
   ▼
Karma（絵にする）
   ├─ ビューポートで確認 …… Hydra デリゲートとして
   └─ karma LOP から書き出し  MPlay / ディスク
   ▼
出力
   ├─ .exr（画像・AOV）
   └─ .usd（シーンそのもの。他の DCC やレンダラに渡せる）

注目していただきたいのは、いちばん下の出口が2つあることです。 Solaris は「Houdini でレンダリングするための場所」であると同時に、 「USD としてシーンを書き出すための場所」でもあります。 チームで使うときや、あとから別のレンダラに差し替えたくなったときに効いてくるのはこちらです。

Karma は何なのか

Karma は Houdini に入っているレンダラです。光を追いかけて絵を作る、いわゆるパストレーサですね。

ありがたいのは、ビューポートの表示と最終レンダリングが同じ Karmaだという点です。 ビューポートの表示方法を Karma に切り替えると、そこに出るのは本番と同じ計算による絵になります。 「プレビューでは良かったのに、書き出したら違った」が起きにくいのはこのためです。

仕組みとしては、USD 側の描画窓口である Hydra に Karma を差し込む形になっています。 差し込むものを替えれば表示も替わる、という作りです。この差し込むものを「レンダーデリゲート」と呼びます。

エンジンは2種類あり、パラメータひとつで切り替えます。

Karma CPUKarma XPU
使うハードウェアCPU のみCPU ＋ GPU
速度遅い速い
機能の多さ多い。挙動もより正確CPU に追随する形で、いくらか少ない
VEX シェーダ限定的に使える使えない
マテリアルPrincipled shader / MaterialX / USD Preview SurfaceMaterialX と USD Preview Surface のみ
GPU の条件—現状 NVIDIA のみ

切り替えは Karma Render Settings LOP または karma LOP の Engine Settings（内部名 engine）で行います。実機で確認したところ、 メニューの値は cpu と xpu の2つで、既定は cpu でした。

Mac で作業されている場合、XPU は現状 NVIDIA GPU 前提なので、 実質 CPU 一択になります。このシリーズも CPU を基準に書きます。

覚えるノードは、思ったより少ない

LOP のタブメニューにはかなりの数のノードが並んでいますが、最初に覚えるものは 役割ごとに分けると数えられる程度です。以下は Houdini 22.0.368 に実在することを 確認したノードタイプ名です。

役割ノード（内部名）
ジオメトリをステージに載せる sopimport / sopcreate / sopmodify
USD ファイルを読み込む・レイヤーを操作する sublayer / layerbreak / configurelayer / edittargetlayer / loadlayer
マテリアルを作る・割り当てる materiallibrary / assignmaterial / componentmaterial / materiallinker
レンダー設定と出力 karmarendersettings / karmarenderproducts / karmastandardrendervars / usdrender_rop
レンダリングを実行する karma

先にひとつ、引っかかりどころ

この表を作るときに実機で気づいたことがあるので、先に共有しておきます。

レンダリングを実行するノードの名前は、そのまま karma です。 ところがノードタイプの一覧を機械的に引くと、これだけ出てきません。 「karma」で絞り込むと karmarendersettings などはずらりと並ぶのに、肝心の karma が抜けています。

無いわけではありませんでした。名前を指定して直接問い合わせると、ちゃんと返ってきます。 Houdini 22.0.368 でパラメータ 80 個、18.0 からあるノードです。 一覧に出ないだけで、タブメニューからは普通に置けます。

そして、このノードの正体はドキュメントに明記されています。

Karma LOP は rendervar / renderproduct / karmarendersettings / usdrender_rop の機能をひとつにまとめたもので、Karma 固有の設定を含めて 1か所で構成できるようにしたノードです。

つまり karma LOP は4つのノードの詰め合わせです。 最初は karma ひとつで通し、パイプラインとして分業したくなったら 中身の4つに分解する、という順番で覚えるのがよいかなと思っています。

既定値をいくつか

手を動かす前に頭に入れておくと迷わない既定値です。いずれも Houdini 22.0.368 の karma LOP で確認したものです。

パラメータ（内部名）既定値ひとこと
Camera（camera）/cameras/camera1 ステージ上のカメラのシーングラフパス。ここが合っていないと何も映りません
Resolution（resolution）1280 × 720 Render Settings 側の既定も同じです
Output Picture（picture）$HIP/render/$HIPNAME.$OS.$F4.exr $OS はノード名。連番なら $F 系を必ず含めます
Rendersettings Primitive Path（primpath）/Render/rendersettings 設定が USD 上のどこに書かれるか。karmarendersettings 単体だと /Render/$OS です
Engine Settings（engine）cpuCPU / XPU の切り替え
Primary Samples（samplesperpixel）9CPU のときのピクセルあたりのサンプル数
Path Traced Samples（pathtracedsamples）128XPU のときのサンプル数

Primary Samples と Path Traced Samples が並んでいて、どちらを触ればいいのか 迷いやすいところですが、エンジンによって使われる方が変わります。 CPU なら前者、XPU なら後者です。片方をいくら上げても効かない、という事故はここで起きます。 サンプリングは第8回でまとめて扱います。
