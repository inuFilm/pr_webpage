レイヤーと Layer Break — 編集はどこに書かれるのか

houdini-solaris / 2026-08-19

出典: SideFX 公式ドキュメント How LOPs work / Layer Break / Merge LOP / USD ROP。 このページは上記を日本語で要約・再構成した学習メモです。挙動は Houdini 22.0.368 で実際にネットワークを組み、 書き出したファイルとレイヤーの中身を確認しています。

この記事で扱うこと

  • LOP の編集がどこに書き込まれるのか（＝レイヤー）
  • layerbreak が何をしているのか。パラメータが1つも無いのに、いちばん効くノードです
  • sublayer / merge / configurelayer / edittargetlayer のノード解説
  • 実際に書き出して、ファイルの中身が本当に変わることを確認します

まず、USD には「消す」が無い

ここから話が始まります。USD では、いちど書かれたものを消すことができません。 できるのは「上から別のことを書く」だけです。

だから「このライトを消したい」は、USD では 「このライトをオフにする、という一文を上に足す」になります。 元のライトはそのまま残ります。

この「上に足していく紙」がレイヤーです。前回の Photoshop の喩えがそのまま使えます。 下の絵は消せないけれど、上に不透明な四角を1枚置けば隠せますよね。それと同じことをしています。

ルールは3つだけ

公式ドキュメントの説明を、実際に手を動かすときに必要な形に絞ると、覚えることは3つでした。

#ルール意味
1 ノードから出てくるのは重ねた結果 どのノードを見ても、そこまでを全部重ねた「完成形のシーン」が見えます
2 書き込み先はいちばん上の1枚 ノードが編集を書くのは、常にいちばん強いレイヤーです。だから書いたことが必ず見えます
3 ディスクのファイルは絶対に書き換えない 読み込んだ .usd の上に新しい1枚が作られ、そこに書かれます

ルール2の「いちばん上の1枚」を、Houdini はアクティブレイヤーと呼びます。 パラメータ名やパネルにこの言葉が出てきたら、「いま書き込まれている紙」のことだと思ってください。

ルール3が地味に大事です。他所からもらった .usd をいくらいじっても、元ファイルは無傷です。 変更はぜんぶ、その上の新しい紙に載ります。

Layer Break — 保存されるのはここから下だけ

やっと本題です。layerbreak がやることは2つだけです。

  1. ここから新しい紙を1枚おろす（以降のノードはその紙に書く）
  2. それより前の紙に「これは保存しない」と印をつける

そしていちばん大事なのは、見た目が何も変わらないことです。 ビューポートの絵は Layer Break の前後で完全に同じままです。変わるのは .usd に書き出したときに、何がファイルに入るかだけ。

USD ROP がレイヤーをファイルに書き出すとき、Layer Break より前のものはすべて捨てられます。

実機で get_node_card を引いたところ、layerbreak のパラメータは実質ゼロでした （セパレータとラベルだけで、設定する値がありません）。置くか置かないか、位置をどこにするか。それが全部です。

何が嬉しいのか

公式ドキュメントが挙げている例が分かりやすいので、そのまま借ります。

あなたは照明担当です。レイアウト部から landscape.usd が届きました。 中には地形と、レイアウト担当が仮で置いた /lights/scratch_sun1 という仮ライトが入っています。

あなたの仕事は「仮ライトを消して、本番のライトを組む」こと。 そして納品するのは lighting.usd、つまり照明の変更だけが入ったファイルです。 地形をもう一度書き出したら、二重に持つことになってしまいます。

ここで Layer Break を1個置くだけで、それが実現します。

実機で確かめました

図のとおりのネットワークを Houdini 22.0.368 で組んで、レイヤーの中身を直接読みました。

1. レイヤースタックの中身

いちばん下流のノードでレイヤーを並べたところ、こうなっていました。上が強い順です。

順そのレイヤーに書かれているもの正体
0（ほぼ空）Houdini の内部用
1（ほぼ空）Houdini の内部用
2/lights/scratch_sun1、/lights/key_dome Layer Break より後
3/from_layout、/lights/scratch_sun1 Layer Break より前

scratch_sun1 が2枚に出てくるのが分かりますでしょうか。下の紙にライト本体があって、 上の紙に「止める」という指示だけが載っています。これがルール1〜3の合わせ技です。

ノードは5個なのにレイヤーは4枚で、しかも2枚が空でした。 「1ノード＝1レイヤー」ではないので、数が合わなくても気にしなくて大丈夫です。

2. 中身の書かれ方が違う

同じ scratch_sun1 なのに、2枚での書かれ方がはっきり違いました。

Layer Break より前（下）Layer Break より後（上）
書き出しの種類def（定義）over（上書き）
持っている情報型、スキーマ、各種設定active の1つだけ

def は「これを作ります」、over は「すでにあるものに、これだけ足します」です。 Layer Break より後で触ったものは、こうやって差分だけになります。

上の紙を実際にテキストで書き出すと、こうなっていました（長いので抜粋です）。

#usda 1.0

over "lights"
{
    over "scratch_sun1" (
        active = false
    )
    {
    }

    def DomeLight_1 "key_dome"
    {
        color3f inputs:color = (1, 1, 1)
        float inputs:intensity = 1
        ...
    }
}

地形（from_layout）は影も形もありません。仮ライトも active = false の一行だけ。 まさに「照明の変更だけが入ったファイル」になっています。

3. 書き出したファイルも変わる

最後に、USD ROP から実際にファイルへ書き出して、layerbreak1 をバイパスした場合と比べました。

Layer Break書き出されたファイル
有効1,691 バイト
バイパス2,162 バイト

差の 471 バイトが、地形と仮ライトの本体です。ノードを1つバイパスしただけで、 画面の絵は一切変わらないまま、ファイルの中身が増えました。

ノードごとの解説

Layer Break layerbreak

やること新しい紙をおろし、それより前を「保存しない」と印をつける
入力0〜1
パラメータ実質ゼロ（ラベルとセパレータのみ）
見た目への影響なし。ビューポートは変わりません
置く場所「ここから自分の仕事」という境目。他所から読み込んだ直後が定番です

SubLayer sublayer

やること.usd ファイルをレイヤーとして重ねる。既存レイヤーの削除・入れ替え・並べ替えもできます
入力1つ目＝重ねる先のステージ、2つ目＝マルチ入力（他のノードチェーンのレイヤー）
入力の順番左が弱く、右が強い
要のパラメータファイルパス、handlemissingfiles（既定は error）
向いている場面他部署の .usd を持ち込む。シーンの入口

「重ねる」だけなので、読み込んだものはその場所にそのまま出てきます。 「別の場所にぶら下げたい」ときは Reference のほうで、これは第4回で扱います。

Merge merge

やること複数のノードチェーンのレイヤーを、1つのレイヤースタックにまとめる
入力いくつでも。後ろの入力ほど強い
要のパラメータmergestyle（既定 flattenloplayers）、striplayerbreaks

mergestyle は7種類ありますが、最初に知っておきたいのは2系統あるということだけです。

系統やること速さ
Separate 系レイヤーを重ねるだけ。枚数はそのまま速い
Flatten 系レイヤーを1枚に潰す遅い

ドキュメントには「潰すのはディスクに書き出すときでよく、その処理は USD ROP 側でもできる」という趣旨の 注意が書かれています。ネットワークの途中で潰すと、そのぶん毎回コストを払うことになるからですね。

striplayerbreaks（Strip Layers Above Layer Breaks）も覚えておくと効きます。 1か所から枝分かれして、また Merge で合流する形（ダイヤ型）を組むと、同じレイヤーが両方の枝から来て重複します。 枝の先頭に Layer Break を置いてこれをオンにすると、その重複を落とせます。

Configure Layer configurelayer

やることレイヤーのメタデータを設定する。保存先ファイルパスを決めるのがここ
要のパラメータsetsavepath ＋ savepath（既定 $HIP/usd/$OS.usd）
その他デフォルトプリム、単位（metersperunit 既定 0.01）、上方向軸（既定 z）、コメント
チェックボックス第1回と同じで、オンにしたものだけが書き込まれます

メモリ上のレイヤーに保存先を与えると、書き出しのときにそのレイヤーが別ファイルになります。 「地形は landscape.usd、照明は lighting.usd」といった分け方は、ここで決めます。

ディスクから読み込んだレイヤーには、読み込み元のパスが最初から入っています。 自分で決める必要があるのは、LOP の中で新しく作ったレイヤーだけです。

Edit Target Layer edittargetlayer

やることルール2の例外。下のレイヤーを直接いじったことにする
入力1（必須）
使い方ノードの中に潜って、そこで編集を組みます
向いている場面「上に重ねる」ではどうにもならないとき。最後の手段です

Solaris は USD の Edit Target という仕組みを使いません。かわりにこのノードが、 対象レイヤーを取り出して編集し、元の位置に差し替える、ということをやっています。 仲間に loadlayer（Load Layer For Editing）と layerreplace（Layer Replace）があります。

実機で気づいたこと

Prune の既定は「消す」ではなく「隠す」

prune でライトを止めようとして、最初うまくいきませんでした。 パターンは合っているのに、シーングラフにライトが残ったままだったんです。

原因は method パラメータで、既定値は makeinvisible（Make Invisible）でした。 deactivate（Deactivate）に変えたら、ライトはツリーからも消えました。

Method何が起きるか
Make Invisible （既定） ツリーには残る。ビューポートとレンダリングには出ない
Deactivate ツリーからも消える。以降のノードからも触れなくなる

下流でそのプリムを名前で指定したい場合は Make Invisible、完全に無かったことにしたい場合は Deactivate、という使い分けになりそうです。

Apprentice が書き出す USD は .usdnc になる

.usda（テキスト形式）で書き出そうとしたのですが、できたファイルは lighting.usdnc でした。 拡張子が勝手に変わります。中身を覗くと、こう書いてありました。

Houdini Non-Commercial USD File. Tampering with this text consti...

Apprentice で書き出した USD は非商用形式で包まれ、テキストとして読めなくなります。 この記事の .usda の中身は、ファイルからではなくメモリ上のレイヤーから直接読み出したものです。 ファイルサイズの比較だけは、書き出した .usdnc の実測値です。

Indie や Commercial では普通の .usd / .usda / .usdc が出ます。 検証機が Apprentice なので出た制約で、Solaris の仕様ではありません。 ただ、他の DCC に渡す前提でワークフローを組むなら、ここは必ず本番ライセンスで確認したほうがよいところです。

レイヤー一覧には Houdini の UI 用レイヤーが混ざる

レイヤーを一覧すると 14 枚も出てきて驚きましたが、大半は Solo Lights / Purpose / Viewport State / Selectability / Visibility and Activation といったビューポート操作用のレイヤーでした。

シーンの中身が入っているのは名前が単に LOP になっているものだけです。 初めてレイヤーのパネルを開くと面食らいますが、名前が付いているものは読み飛ばして大丈夫です。

詰まりやすいポイント

  • Layer Break を置いても何も変わらない → それが正しい挙動です。 違いが出るのは書き出したときだけ。慌てて位置を変えないでください。
  • 書き出したファイルに余計なものが入る → Layer Break が無いか、位置が上流すぎます。 「ここから自分の仕事」の直前に置きます。
  • 読み込んだ USD を直接書き換えたい → できません。上に重なる新しいレイヤーに書かれます。 どうしても、というときだけ edittargetlayer です。
  • Merge したら重い → mergestyle が Flatten 系になっていないか確認します。 潰すのは書き出しのときで足ります。
  • Prune したのに残っている → method が既定の Make Invisible のままです。

次回

レイヤーの話が片付いたので、次はシーングラフそのものを読む回です。 Scene Graph Tree と Details パネルの見方と、Solaris 全体で使い回せる プリムパターン（%kind:component のような書き方）を扱います。 「どのプリムを選ぶか」を書けるようになると、以降のノードがまとめて楽になります。
